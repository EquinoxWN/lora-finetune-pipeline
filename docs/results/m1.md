|---|---|---|---|---|---|---|---|
| Base, zero-shot (instruction + intent list) | 0.1828 | 0.1859 | 42.9% | 418.6 | 237.6 | not recorded | not recorded |
| Base, few-shot (+ 1 example per intent) | 0.2615 | 0.2802 | 39.2% | 2,482.6 | 1,067.5 | not recorded | not recorded |

Training (QLoRA, NF4 4-bit base, LoRA r=16 on 7 projections, 8,798,208 trainable of 323,917,696
parameters, one epoch, effective batch 16): 569 steps over 9,102 examples (463,684 tokens) in
**787.1 s (13.1 min)**, peak VRAM 3,240 MiB allocated / 5,412 MiB reserved, **6.98 Wh** of GPU
energy. Training loss 2.935 -> 0.054; validation loss 6.157 -> 0.066. Adapter: 33.6 MiB. Model
load: 3.1 s, 430 MiB footprint in 4-bit.

Cost (measured GPU time on this machine; no cloud prices): the adapter answers in 52.3 ms against
237.6 ms (zero-shot) and 1,067.5 ms (few-shot), so the 787 s training run is repaid after
**4,248 queries** against zero-shot and **776 queries** against few-shot. The prompt is 9.4 times
shorter than zero-shot and 56 times shorter than few-shot.

Most frequent remaining mistakes of the adapter (gold -> predicted): `pending_transfer` ->
`transfer_not_received_by_recipient` (11), `balance_not_updated_after_bank_transfer` ->
`transfer_not_received_by_recipient` (6), `card_arrival` -> `card_delivery_estimate` (5),
`exchange_via_app` -> `fiat_currency_support` (5). These are neighbouring intents; grouping them
is the M3 error analysis.

## What the numbers say (Analyze)

- **Fine-tuning wins clearly on this task and model.** The 0.5B model prompted with 77 intents
  invents intent names in about 40% of answers (for example `revert_card_payment`,
  `decline_transfer`, `allowed_intent`); examples help (+7.9 points) but cost 6 times the prompt
  tokens. A 13-minute QLoRA run lifts accuracy from 26.2% to 91.2% and nearly removes invalid
  answers (0.07%).
- **It is also cheaper per query.** Latency here is dominated by the number of forward passes and
  by prompt length at batch 16 (few-shot, 2,483 tokens, is the slowest); the adapter's 45-token
  prompt and 4-token answer make it the fastest mode, so training pays for itself after fewer than
  800 few-shot queries.
- **Reproducible:** the 2026-10-10 training run and the stopped 2026-10-09 run logged identical
  losses at steps 25 to 150 (2.9354, 0.9031, 0.4691, 0.3585, 0.2860, 0.2312).
- **Defects found and their root causes:**
  1. Two source labels are spelled inconsistently (`Refund_not_showing_up` in 202 rows,
     `reverted_card_payment?` in 201 rows); the strict parser stopped the run. Fixed by
     canonicalising labels during curation, counted in the report.
  2. Fine-tuned generation was as slow as few-shot in the lite run (374.5 ms/query) although its
     prompt is 56 times shorter. Root cause: gradient checkpointing makes Transformers set
     `use_cache=False` when training starts, and it stayed off for generation, so every new token
     recomputed the whole sequence.
  3. The training phase's reserved-VRAM peak included memory cached by the previous phase.
  4. The first full run was stopped from outside the process at training step 150 of 569, after
     both prompting phases (67 minutes) had finished but before anything was written, so all of it
     would have been lost. Two earlier attempts were refused by the memory preflight (1,407 and
     845 MiB free RAM against the 1,500 MiB floor) while other builds were running.
- **Not recorded:** peak VRAM, GPU energy and confusion pairs of the full-set zero-shot and few-shot
  phases (their process was stopped before writing them; the accuracy, macro-F1, invalid rate and
  time were logged and are in `m1-prompting-recorded.json`; prompt tokens were recomputed exactly
  from the tokenizer). Energy break-even is therefore given only for the lite run.

## Improve

| Change | Measured effect |
|---|---|
| Canonical labels in curation | 403 rows fixed (323 train, 80 test); 77 intents, as in the dataset paper |
| `for_inference()`: KV cache on and gradient checkpointing off after training | Fine-tuned latency 374.5 ms/query (lite, batch 8, no cache) -> 52.3 ms/query (m1, batch 16, with cache); now the fastest mode |
| `torch.cuda.empty_cache()` at the start of each measured phase | Fine-tuned evaluation reserved VRAM 5,350 MiB (lite, included training's cache) -> 1,066 MiB (m1) |
| Training checkpoints every 50 steps (`torch.load(weights_only=True)`), partial results after every phase, `--reuse` for recorded prompting results | A stopped run now loses at most 50 steps; the m1 rerun repeated only training and the fine-tuned evaluation (about 16 minutes instead of 83) |
| Memory preflight (exit 3) | Refused two loads that would have pushed the machine into swap |
